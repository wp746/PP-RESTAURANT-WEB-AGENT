# PP Restaurant Web Studio
## 《门店素材采集与品牌网页生成 SOP》

**版本**：1.0（与《餐饮品牌线上门面设计总纲 v1.0》配套）  
**流程定位**：从“到店采集一个 ZIP”到“交付一套可验收的完整网站”  
**项目原则**：文化第一、视觉第二、交互第三、展示第四  
**本 SOP 当前性质**：可直接交给采集人员、智能体与开发人员执行的流程规范；不等同于已经部署的自动系统  
**默认输出**：每店一套定制网站；以内部设计验收为先，另行确认后公开发布。

---

# 0｜流程总览

```text
用户上门采集 + 老板打包资料
         ↓
P0 资料接收与完整性核对
         ↓
P1 文件识别、影像盘点、菜单结构化
         ↓
P2 事实与版权核验（形成事实台账）
         ↓
P3 门店 DNA 与文化研究（必要时全网查证）
         ↓
P4 文化命题、品牌文案、产品解说与 IP 候选
         ↓
P5 艺术指导：字体、色彩、排版、主视觉、摄影
         ↓
P6 客群路径、交互设计与完整展示结构
         ↓
P7 真正实现 HTML/CSS/JS + 素材资产
         ↓
P8 自动测试 + 实际截图 + 人工视觉复核
         ↓
P9 用户设计验收、调整迭代
         ↓
P10 商家事实/版权/发布确认（独立流程）
         ↓
正式网址 + 分享封面/二维码 + 交付归档
```

每个 P 阶段必须输出指定成果，关键事实或素材不足时仍可进入**注明不完整的内部预览**，但不可悄悄升格为商用发布。

# 1｜P0 上门采集：你负责拍什么，老板负责给什么

## 1.1 责任分工

| 事项 | 采集人员（你） | 老板/门店 | 智能体 |
|---|---|---|---|
| 门头、环境、产品实拍 | 现场采集、命名、留原图 | 配合场地、确认拍摄/使用权限 | 识别与设计组织 |
| 基础信息及联系方式 | 收集并核对 | 提供正式资料、最新状态 | 录入并校验格式 |
| 菜单、价格、产品描述 | 拍摄菜单并核对文字清晰 | 提供确认版及推荐菜 | 结构化、发现冲突 |
| 历史、企业文化、店名缘起 | 录音/记录可选 | 根据真实经历提供和确认 | 提炼、不编造 |
| Logo、现有 IP、VI | 拷贝原件 | 提供使用授权与规范 | 优先沿用 |
| 团购、企微、会员、导航 | 保存官方有效链接/二维码 | 确认对应账号、入口、有效期 | 配置并测试 |

## 1.2 必备信息（缺失可做概念页，不能发布）

- 门店正式名称、经营品类、实际所在地和门店数量（单店/连锁）。
- 地址和地图入口（含选择哪家分店）、电话、营业时间及休息日。
- 最新的菜单与价格/单位/规格；至少 1 款标为招牌的产品。
- 门头/招牌照片、产品照片、至少一张可用空间照片（空间尚未拍摄时须说明）。
- 需要启用哪些行动：导航、电话、团购、咨询、企微、会员、预约；这些入口是否已经真实存在。
- 店铺想强调的经营目标（例如到店、品牌、团购或预订）及主要顾客。
- 拍摄与发布使用授权、商家审核联系人。

**选填但高价值**：老板真实故事、店名缘起、工艺介绍、顾客常问问题、菜单推荐组合、素材对应的店内区域、品牌旧照、视觉资产、制作视频。

## 1.3 建议拍摄镜头清单

| 类别 | 推荐镜头 | 质量底线 | 页面可能用途 |
|---|---|---|---|
| 门头 | 正面全景 + 招牌特写 + 街道入口 | 真实门牌可辨、避免反光遮字 | 身份确认、导航情境 |
| 空间 | 入门视角 + 主就餐区 + 包间/座位 + 真实细节 | 光线真实、说明区域，不人为编造 | 氛围及聚餐决策 |
| 招牌菜 | 完整器皿 45°/正面 + 俯视 + 局部细节 | 不切锅碗盘、菜品可辨 | 首屏主视觉、产品详情 |
| 其他菜 | 统一菜名对应照片 + 规格参照 | 对应真实售卖款，不混菜 | 菜单与推荐 |
| 制作工艺 | 加工、出锅、上桌动作 | 先取得拍摄使用许可 | 文化、技法介绍 |
| 品牌细节 | Logo、招牌字、器具、包装、墙面图案 | 授权明确、无遮挡 | 字体/色彩/点缀依据 |

采集建议：原图直传；保留横、竖构图；不用截图代替原片，不叠滤镜；同一道菜至少包含完整器皿图和产品细节图，照片文件名有明确对应关系。

# 2｜P1 识别、归档与素材技术检查

**输入**：原始 ZIP / 文件夹 / 附加说明。  
**动作**：

1. 解压到独立项目目录；保留原始包只读副本，防止图片被误覆盖。
2. 建立 `asset-manifest`：ID、原文件名、文件路径、类型、分辨率、横/竖、实际主体、所属门店/菜品、来源、授权状态、可用位置、主体安全区、缺点。
3. 将菜单 OCR/提取为结构化表并与照片对应，识别不清的价格、单位、菜名标“待核实”；不能凭图片或常识猜价格。
4. 识别同名文件、重复图、低像素图、截图、水印图、倒置、色偏、严重失焦和版权不明图。
5. 识别 Logo/字体资产是否可网页嵌入，保留许可和原格式。
6. 检测是否包含顾客隐私、员工敏感信息、未上架菜品、外部 API 密钥等；不放进公开页面。

**输出**：`asset-manifest.csv` / `asset-manifest.json` + `素材缺项清单.md` + 整理后的菜单草表。  
**失败回退**：若照片不足，先按真实现有照片做布局概念；缺空间图时不伪装成实景。关键缺失列出最高优先级 3–5 条即可，不把无关问题全部抛回老板。

---

# 3｜P2 事实、素材权利、链接三重核验

**输入**：采集资料、菜单草表、素材台账。  
**执行**：

- 建立 `事实台账.md`：每一条对外陈述必须关联“来源文件/谁确认/更新时间/级别”。
- 分 `F1_已确认`、`F2_外部通用知识`、`C1_原创概念`、`X1_演示占位`。
- 同时维护 `缺失与冲突.md`：菜单价格冲突、地址多版本、照片和菜名对应不明、奖项无证明、团购失效等。
- 可点击链接逐一标注 `verified / not_tested / invalid`；商家给出的短链接先核实最终目的地。
- 标记图片/字体/Logo 的授权状态，不能因原图在压缩包里就默认有对外发布权。

**输出**：事实台账、渠道检查表、素材授权表、待老板确认的精简问题。  
**闸门**：未确认的企业历史、菜单价格、地图和联系方式不进入公开成品。内部测试可以模拟，但页面须标识“模拟资料/概念图”。

# 4｜P3 文化研究与品牌 DNA 建立

**输入**：事实台账、产品与环境实拍、老板原话、品牌资产。  
**必要时研究**：地方饮食文化、料理技法、传统食具、消费习惯及行业背景。优先官方资料、权威出版物、可靠报道；记录来源网址、发布日期、访问日、具体可支持的观点。

**禁止事项**：搜索到另一家品牌的“创始故事”后，直接写成本店故事；用没有来源的传奇人物、奖项、古方、经营年份给新店增加“文化感”。

**分析顺序**：

1. 经营身份：这家店与同品类门店有哪些**可证明**的不同？
2. 料理逻辑：产品主角、工艺、味觉、器皿、真实吃法是什么？
3. 地域与场景：文化背景怎样影响顾客体验？
4. 目标客群：顾客第一次看到网页最想解决什么？
5. 品牌命题：一个短命题能否贯穿标题、影像、动效、产品详解？
6. 候选 IP：是继续使用现有品牌符号，还是有必要提出原创概念？

**输出**：`Brand-DNA.md`、`文化研究来源.md`、`品牌叙事与文案草案.md`。  
**闸门**：用户/商家能看出叙事为何属于“这家店”而非任意餐馆；否则必须重做 DNA。

**范例（只用于测试，非经营事实）**：旺角肥肠鸡可把肥肠与鸡肉的口感对照、锅气、围桌文化作为主线；“阿旺”可作为原创 IP 提案。店龄、创始人、营业资料没有核实，不得写成真实历史。

# 5｜P4 内容策略：品牌文化、菜品解说、顾客建议

**输入**：Brand DNA、菜单和事实台账。  
**输出**：`网站内容母稿.md`，分三个层级：

### 5.1 品牌层

- 店名和品类识别语；1 句品牌主张；店名或理念的真实来处。
- 经营者故事/真实文化背景（没有时可以选择“食物文化”，不能硬编企业史）。
- 合理的章节命名、品牌语气、可用的真实引用。

### 5.2 产品层

每道重点菜形成资料卡：`菜名 / 产品照片 ID / 真实价格与规格 / 菜品主要原料 / 味型 / 工艺特点 / 推荐对象 / 搭配建议 / 价格和内容核验状态`。

没有依据时，“秘制”“现杀”“零添加”“养生功效”“某地直供”等需删除或标成待核实，不能当营销修饰自动添加。

### 5.3 顾客决策层

- 新客点单路径：第一次来怎样选择、主菜与配菜如何搭配。
- 人数/场景建议：以商家提供的套餐、份量、实际菜单为依据；未知时不生成精确价量承诺。
- 口味和忌口/过敏提示：只使用可信的已确认资料，不编造。
- 用餐到店指南：地址、营业时间、停车、预约、服务须知按商家资料配置。

**闸门**：任意一段文化或营销文案都能追溯到来源事实、品类研究或明确的原创提案；不得混淆。

# 6｜P5 艺术指导：不可跳过的设计计划

**先提交设计计划，后写网页代码**。这不表示必须让老板审阅繁琐的技术文档；但生成器内部必须记录决策，否则容易退化为套模板。

### 6.1 设计计划必备字段

| 项 | 必须输出的内容 |
|---|---|
| 文化隐喻 | 1 个核心概念和证据链 |
| 主角 | 首屏产品/门店/制作影像及对应资产 ID |
| 构图 | 桌面/手机不同的视觉路线，前中后景和主体安全区 |
| 字体 | 品牌字、展示字、正文字、数字字、授权/回退字体 |
| 色彩 | HEX、使用比例的初步意图、与实物或 VI 的关联 |
| 点缀 | 图形、纹理、IP 元素各自为什么存在 |
| 动效 | 一个主导机制，触发方式、静态和减少动效降级 |
| 产品摄影 | 每一张真实图如何使用、不允许改变的食材特征 |
| 风险 | 无授权、缺字、主图不够完整、空间照片缺失等 |

### 6.2 主标题字设计分支

适合独立书法题字时，生成：`标题字_透明PNG.png`（2×–3×像素）、预览图、可访问 HTML 文字、图像尺寸与适配规则；可另交 SVG/WebP。**不适合书法的门店不要强行生成**。

### 6.3 设计差异验证

如果当前方案套在烘焙、咖啡和火锅三个不同品牌上都成立，应当怀疑是通用模板。要求回看：字体是否只换名称，首屏是否只换图，配色是否只是行业刻板印象，互动是否真正体现品类差异。

**输出**：`design-plan.md`、`字体与颜色规范.md`、`主视觉/手机桌面构图稿`、`缺图与摄影补采建议.md`。  
**闸门**：无法解释“为什么属于这家店”的视觉项，要删或重新设计。

# 7｜P6 UX 与信息架构：从顾客问题反推操作

**输入**：文化/设计计划、实际菜单、用户目标、确认的联系入口。  
**主要任务**：

1. 绘制顾客路径：认出品牌 → 理解招牌 → 判断适不适合自己 → 选择产品 → 联系/到店。
2. 基于品牌属性决定章节数量、顺序、阅读节奏和信息密度，不固定六屏，不机械把“企业文化”放在第一屏正文。
3. 为每个可交互控件编写：`触发 → 系统反馈 → 空值/失败处理 → 移动端行为 → 键盘行为`。
4. 将模拟状态与真实事务隔离：演示“预约/价格/优惠”明确模拟，不发送真实支付或订单。
5. 给出信息快速可达性：首屏可辨店名、品类、主动作；菜单、地址、营业时间与电话须能够直接找到。

### 7.1 品类特有交互示例

| 门店 | 候选交互 | 必须依赖的数据 |
|---|---|---|
| 肥肠鸡/火锅 | 人数、辣度、加菜、点餐建议 | 真实菜单、规格、可选辣度和售价 |
| 烧烤 | 串品类别、组合和时段 | 产品规格、真实营业时间 |
| 面食 | 汤底、浇头、辣度 | 实际可选项、价格与口味说明 |
| 烘焙 | 口感、原料、产品搭配 | 商家产品说明、真实保存建议 |
| 咖啡/茶饮 | 风味偏好、冷热、甜度 | 真实配方/产品可选项 |
| 宴席 | 包间/人数/套餐浏览 | 真实包间照片、套餐和咨询渠道 |

**输出**：`site-map.md`、`interaction-spec.md`、`CTA-配置表.md`。  
**闸门**：禁止表面“有交互”却无法用真实数据支撑、点击无反馈或无法返回的设计。

# 8｜P7 网站实现：交付的是工程不是设计说明

**实现建议**：第一版优先用可静态托管、手机优先的 HTML/CSS/JS，或清晰组件化的前端工程；不因复杂框架而增大部署难度。根据以后多店自动化规模再演进组件化生成器。

### 8.1 真实站点技术要求

- 网站的**事实数据层**与**设计表现层**分离：未来改菜单不应重新手工改大量页面代码。
- 每张图片有 ID、用途和合适的格式；主图加载策略、尺寸和移动端主体安全区明确。
- 所有字体具备备用字族；定制 PNG 标题不替代 HTML 标题语义。
- 不依赖不可用的本地文件路径、临时沙箱地址、未经许可的付费组件或不稳定的外链图源。
- 外部地图、电话、团购、企微与会员入口只使用经核对的真实值；隐藏资料缺失的动作。
- 适配鼠标、触屏、键盘；弹层支持关闭和焦点管理；减少动效时仍然完整可读。
- API 密钥、发布凭据、企微 Secret、商家敏感数据只保留在服务端，不进入 HTML 和浏览器 JS。

### 8.2 避免之前出现的“白底文字”交付事故

两种方式二选一，并**在交付的实际路径重新打开测试**：

**方式 A：单文件 HTML 预览**——全部必要 CSS、JS 与核心演示资产内置；适合无需服务器的方案验收。

**方式 B：完整目录 ZIP**——保留 `index.html / assets / styles / scripts`，正确使用相对路径；整个文件夹解压后打开/托管，禁止只把 HTML 文件单独发给客户。

无论哪种，真正的上线构建可另外做优化。`有 HTML 文件 ≠ 已制作完整网站 ≠ 已发布公网网址`，三者在进度表中分开报告。

**输出**：可运行网页工程、演示入口、构建说明、素材资产、版本说明。

# 9｜P8 真实浏览器验收：必须看见页面再算完成

### 9.1 每次最少的自动化检查矩阵

| 项目 | 视口/操作 | 合格条件 | 失败处理 |
|---|---|---|---|
| 页面加载 | 桌面及手机打开实际交付文件 | CSS、JS、字体及重要图片可加载 | 修路径或改交付格式 |
| 360 / 390 手机 | 首屏+全页截图 | 无横向溢出；主图不消失、按钮无遮挡 | 重做窄屏构图和盒模型 |
| 768 平板 | 首屏及交互截图 | 版面不拥挤、不出现断裂 | 单独调整栅格与折行 |
| 1440 桌面 | 首屏+全页截图 | 主视觉完整、字与图层次正确 | 调整主视觉/留白 |
| 菜品切换 | 逐项点击 | 图片、名称、描述与售价正确对应 | 校验状态/数据绑定 |
| 配置/推荐 | 更改人数、辣度、加菜 | 反馈正确；预算仅基于真实/注明模拟的数据 | 修计算或隐藏功能 |
| 弹层与表单 | 打开、填写、提交、关闭 | 正常反馈；模拟不声称完成真实订单 | 改提示/修交互 |
| 外部 CTA | 导航、电话、团购、会员/企微 | 目标与商家确认一致；无伪链接 | 移除或补正确链接 |
| 字体与图片 | 主标题、菜名、Logo、锅盘 | 无缺字错字、无遮挡、无关键主体切断 | 换字/改资产与构图 |
| 容错与可访问性 | 无图、字体失败、减少动效、键盘 | 主要信息仍可读、操作仍可用 | 添加降级、焦点/提示 |

### 9.2 性能及兼容性实测

记录实际设备/浏览器/网络条件；检查文字对比度、首屏加载预算、LCP/CLS/INP，避免大图过重。微信、抖音内置浏览器中电话、地图、优惠、会员与分享**要另做真机测试**；未执行时必须标记 `not_tested`。

### 9.3 验收结果只能是三个状态

`PASS / FAIL / NOT_TESTED`。每一项必须提供证据：截图路径、测试步骤、浏览器、结果、已知问题和责任人。不能把 `NOT_TESTED` 写成通过。

**输出**：`validation-report.md` 或 JSON、手机/桌面真实截图、缺陷列表、复测记录。  
**闸门**：核心视觉/交互失败不得转 P9；必须先修复并重新截取交付文件的截图。

# 10｜P9 设计验收与迭代

### 10.1 让用户验收的顺序

1. **文化**：品牌命题准确吗？能不能感受到这家店自己的文化，不是套来的故事？
2. **视觉**：字体、创意、摄影、配色、排版、装饰每一项都能说明与门店的联系吗？
3. **交互**：顾客操作有价值吗？有没有过多动效、操作障碍？
4. **展示**：菜单、环境、价格、导航信息是否完整并清楚？
5. **工程**：手机与电脑都能独立打开并完成关键操作吗？

### 10.2 反馈修订机制

每条反馈记录：`问题截图 / 页面位置 / 严重度 / 修改理由 / 修改内容 / 影响范围 / 复测结果`。视觉修改可能影响字体加载、点击区域、主图主体安全区，故调整后必须重新跑相应检查。

**版本格式建议**：`品牌名_店名_web_v1.0.0`；每次修改保留 `CHANGELOG.md`，不要覆盖老板已经确认的事实资料。

**输出**：用户确认的设计版本 + 尚未确认事项及复测报告。  
**闸门**：设计确认不等于上线授权，二者分开。

# 11｜P10 正式发布与归档（设计通过后才启动）

公开发布前，老板/用户明确确认以下内容：

- 网站具体版本与预览截图；店名、门店信息、菜单价格、优惠有效期。
- 文案中的品牌历史与文化事实，以及是否采用某个原创 Slogan/IP。
- 门头、环境、菜品、Logo、字体/图片版权和人物肖像授权。
- 电话、地图、团购、企微/会员等最终链接已在目标设备核验。
- 公开域名、托管方式、访问范围、必要的备案事项以及后续信息更新责任人。

不必为演示原型购买服务器和域名；长期商用可选择静态托管及自有域名。生成器需要的模型调用和私有素材应由受控后台处理，公开网页不暴露密钥。

**正式交付清单**：源代码、可访问正式网址、已验证二维码/分享封面、授权资产记录、测试报告、数据更新方式、备份与版本记录。

# 14｜给智能体的执行指令（可直接作为生产工作流骨架）

> 你是一名餐饮品牌策略、文化研究、视觉艺术指导、UI/UX 与前端实现的跨职能设计智能体。接收一个门店素材包后，必须先读取全部真实资料、建立素材台账和事实台账，区分商家已确认事实、可核验行业文化、原创创意建议及演示占位。随后提炼每店独有的品牌 DNA，以“文化第一、视觉第二、交互第三、展示第四”为不可变的设计决策顺序。根据门店品类、客群、空间、菜单、品牌资产和经营目标，为该店定制文化叙事、字体、配色、构图、摄影、点缀、动效、交互与信息架构；不得只用一套模板替换店名、色彩和图片。合适时可制作透明 PNG 书法/定制标题字，但必须保留可访问的真实文字与使用权记录。交付一套可运行的完整网站，而非单纯概念稿；先在真实浏览器检查手机桌面渲染、图片裁切、交互反馈、联系方式与素材加载，提供实测截图和 PASS/FAIL/NOT_TESTED 报告。缺乏证据时不得编造门店历史、经营数据、食材特性和任何外部链接；内部概念页必须清楚标记。用户确认设计后，仍需单独取得商家事实、授权和公开发布确认才能上线。
